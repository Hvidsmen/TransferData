# TransferData

ETL-сервис для переноса `DataWH.erp.[Справочники.Контрагенты]` из SQL Server
на Windows-сервере `vm-dwh` в PostgreSQL `analytics`. Полная замена по расписанию,
пакетное чтение, транзакционный откат при ошибке и журнал количества строк.

**Развёртывание на Windows:** [инструкция](windows/README.md).
Windows-аутентификация SQL Server использует учётную запись процесса
`DAICHI\ETLadmin` через Microsoft ODBC Driver 18. Пароль SQL Server в JSON не нужен.
Назначение — `public.contractors`; запуск ежедневно в 02:00 по Москве.
Перед первой загрузкой команда `prepare` создаёт таблицу по структуре источника.

## Разработка

Нужны Python 3.12+ и uv. Из корня проекта:

```sh
uv sync --locked
uv run --locked pytest -q
uv run --locked transferdata validate --config config.example.json
```

В облачной среде используйте `UV_CACHE_DIR=/workspace/.cache/uv`.
Зависимости зафиксированы в `uv.lock`. Файл `config.json`, пароли и `.state`
не включаются в Git. Файл `.env` автоматически не читается.

## Команды

```text
transferdata validate --config config.json
transferdata check --config config.json
transferdata prepare --config config.json --job contractors
transferdata run --config config.json --job contractors
transferdata serve --config config.json
```

`validate` проверяет задания и cron без обращения к БД. `check` выполняет SELECT 1
на обоих подключениях. `prepare` создаёт отсутствующую таблицу PostgreSQL, не
загружая строки. Повторный запуск не меняет существующую таблицу. `run` действительно заменяет данные; сначала проверьте на
тестовой таблице. `serve` запускает встроенный планировщик, первый перенос — по
расписанию. При использовании Планировщика Windows запускайте `run`, а не `serve`;
расписание тогда задаётся в Windows. Не используйте оба планировщика одновременно.

Пароль и логин PostgreSQL передаются через `TARGET_USER` и `TARGET_PASSWORD`;
Windows-скрипт извлекает их из локального DPAPI-файла. PostgreSQL использует
`sslmode=verify-full`: нужен доверенный сертификат на имя/IP сервера; при необходимости
задайте `PGSSLROOTCERT`. SQL Server также требует шифрования и доверенного сертификата.
Сервис не отключает проверки сертификатов.

## Поведение и ограничения

- Полная замена выполняет DELETE и пакетные INSERT в одной транзакции назначения.
  Ошибка откатывает изменения. DDL и TRUNCATE не выполняются.
- Перед записью целевая таблица блокируется от конкурентной записи; обычное чтение
  продолжает видеть зафиксированные данные. Требуется место для журнала транзакций.
- Пустой источник вызывает отказ, сохраняя цель. Очистка пустым источником разрешается
  только при `allow_empty: true`.
- Имена столбцов совпадают по умолчанию. Для выбора/переименования добавьте в задание
  `"columns": {"Код": "code", "Наименование": "name"}`. Типы должны быть совместимы.
  `prepare` переносит выбранные столбцы, типы и NULL/NOT NULL. Ключи, индексы,
  identity, defaults, триггеры и computed-выражения не копируются: загружаются
  готовые значения источника. UUID → uuid, Unicode → varchar/text, двоичные типы
  и SQL Server rowversion → bytea, decimal/money → numeric. Неизвестный тип
  вызывает отказ до создания таблицы. Имена PostgreSQL ограничены 63 UTF-8 байтами;
  для длинных имён задайте `columns`. Схема назначения должна существовать, а
  пользователь — иметь CREATE в ней. Изменение структуры существующих таблиц
  и инкрементальная загрузка не реализованы.
- Триггеры, внешние ключи, generated/identity-столбцы могут требовать отдельной
  подготовки целевой таблицы. Внешние побочные эффекты триггеров не откатываются сервисом.
- Для согласованного среза меняющейся исходной таблицы DBA должен настроить SQL Server
  READ_COMMITTED_SNAPSHOT или предоставить согласованный источник. Сервис не меняет
  настройки SQL Server.
- Один процесс на `lock_directory`, одна реплика. Встроенный планировщик выполняет
  задания последовательно. Пропуски во время остановки не восстанавливаются им;
  автоматических повторов и внешних оповещений нет.
- Журнал содержит статус, число строк, время и тип ошибки; строки данных, параметры
  SQL и пароли не печатаются. Код возврата разового запуска ненулевой при ошибке.
  В режиме `serve` ошибка задания не останавливает планировщик.
- SQLite-тесты проверяют перенос, откат, пустой источник, повторный запуск и
  исполнение планировщиком. Проверка реальных типов, ODBC, Windows-аутентификации
  и соединения с PostgreSQL должна выполняться на vm-dwh.

Дополнительно сохранён драйвер Oracle (`target.dialect: oracle`, `service_name`,
`ORACLE_USER`, `ORACLE_PASSWORD`) и парольный источник pymssql (без `auth: windows`).
Основная конфигурация и инструкция относятся к Windows → PostgreSQL.
