## Новый эксперимент

`tools/sql/Compare-SalesDocumentsNarrow.sql`: исходный вариант SELECT * против
кандидата с двумя полями в **33** временных справочниках/связанных документах.
Это Ссылка и Наименование, поле перечисления либо Номер. Перечень явно задан
по предоставленному коду; выбор полей не строится по догадке об ERP-метаданных.

**Все 77 исходных индексов сохранены в обоих вариантах**, включая 43 индекса
#РеализацияТоваровУслуг. Основная таблица реализаций по-прежнему читается целиком;
составная таблица заказов/заявок на возврат с UNION ALL не меняется. Все 45 JOIN,
поля результата, COALESCE, NULL, фильтры и кратность дубликатов прежние.
Никаких DISTINCT/TOP/уникальности ссылок справочников и новых tenant-фильтров.

Получаем прежнюю процедуру через OBJECT_DEFINITION на vm-dwh и строим две
приватные копии тела, сохраняя живой исходный текст и комментарии. Guard прежнего
опыта проверяет 77/43 индекса, заголовок, выходные ссылки, цели и отсутствие
посторонних записей. Для каждого из 33 чтений дополнительно проверяются
единственный SELECT * INTO, точный FROM и отсутствие новых WHERE/JOIN/алиасов.
При изменении формы исходника остановиться и разобрать текст, не обходить guard.

Выходы: DataWH.document_trial.SalesWide_<GUID> и SalesNarrow_<GUID>.
Исходная процедура и её рабочая таблица не запускаются/заменяются, задания Agent
не меняются; товарные строки и дедупликация рабочего шага не исполняются.
Контекст извлечения остаётся 1CUnloading. Сравнение выполняется до произвольной
дедупликации ROW_NUMBER: её эквивалентность этим опытом не подтверждается.

## Запуск и результаты

После git pull выполнить целиком **Compare-SalesDocumentsNarrow.sql** в новом
окне SSMS на vm-dwh без открытой транзакции, после подготовки ERP-копии и вне
основной загрузки. Нужны те же права, что для предыдущего замера.
По умолчанию @CandidateFirst=0. Если результат обнадёживает, повторить в другом
порядке с @CandidateFirst=1 до решения о рабочем переключении.

Оба извлечения и полная сверка создают нагрузку на ERP, диски, tempdb и журналы.
На каждый запуск остаются две полные копии шапок (раньше около 2,5 GiB каждая).
Сверка всех столбцов/типов и количества копий строк выполняется отдельно от
BaselineMinutes/CandidateMinutes; текст проверяется побайтно с длиной.
Нет общего snapshot удалённых чтений: источник и справочники должны быть готовы
и стабильны на весь опыт. Длительность SQL и удалённых ожиданий не ограничена
локальным LOCK_TIMEOUT=30000. При задержке несколько минут читать диагностику,
а не ждать часами и не отменять вслепую.

Отдельные журналы:

- SalesNarrowRuns — полный RunId/SessionId, времена извлечений и сверки, Status;
- SalesNarrowIndexes — по 77 построенных индексов на каждый вариант;
- SalesNarrowReads — 33 завершённых чтения каждого варианта, время, RowsCopied,
  ReservedPages временной таблицы до её индекса (локальный объём tempdb).

Время чтения включает SELECT INTO, но не отдельный запрос метаданных страниц;
накладные расходы всей инструментализации входят в полное время обоих вариантов.
ReservedMB — выделенные страницы временной таблицы, **не сетевой трафик** и не
точный объём полезных значений. Снижение ReservedMB само по себе не доказывает
ускорение всего извлечения. Исходный view может оптимизироваться по-разному;
выигрыш по времени заявляем только по результату замера.

Во вкладке Messages: название текущего читаемого справочника и индекс N/77.
Для прогресса запустить обновлённый Check-SalesDocuments.sql в другом окне:
он выбирает последний запуск среди двух экспериментов и показывает statement/wait.
Статус running может остаться после отмены и не является доказательством работы.
Session-lock после отмены может сохраняться до закрытия исходного соединения.

Ожидается MATCH, MissingGroups=0, ExtraGroups=0. Пришлите первые три итоговые
таблицы: общий замер, индексы и LookupReadMinutes/LookupReservedMB. Подробная
таблица по 33 чтениям нужна для разбора самых дорогих источников.
Подготовка проверяется статически; реального SQL Server в облаке нет.

Первым baseline: MATCH/0/0, 8,5136 / 7,27828 мин; обратный порядок:
