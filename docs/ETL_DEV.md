# ETL Dev: единый портал

Основной репозиторий развёртывания: `Hvidsmen/TransferData`. Название портала —
**ETL Dev**; Python-пакет и рабочий каталог сохраняют имя `transferdata` для
совместимости с существующей установкой.

Подсистемы остаются разными:

| Подсистема | Адрес | Движок | Очередь / журнал | Worker |
|---|---|---|---|---|
| TransferData | `/transferdata/` | SQL Server → PostgreSQL | `panel_*` | `etlworker` |
| ERP_to_DWH | `/erp/` | SQL Server → SQL Server, staging | `control_*` | `etl_worker` |

Главная `/` — выбор подсистем. Вход, пользователи, порт и оформление общие.
Служебные таблицы находятся в `.state/panel.sqlite3`, но рабочие задания и истории
не смешиваются. ERP-права сохранены: сотрудники видят информацию, изменения
подключений, SQL и запуск доступны суперпользователю. TransferData сохраняет
проверки Django model permissions. Обычные пользователи без `is_staff` в портал
не допускаются. SQL и параметры источников доступны сотрудникам ERP: назначайте
этот доступ только доверенным пользователям.

## Обновление на vm-dwh

Перед обновлением остановите web и оба старых обработчика, а также внешние
планировщики загрузок. Не останавливайте выполняющийся перенос без необходимости:
дождитесь завершения, затем сделайте резервную копию старых служебных SQLite БД.
Существующие config.json, DPAPI-файл и `.state` не удаляйте.

Из каталога TransferData под `DAICHI\ETLadmin`:

```powershell
git pull origin main
py -m pip install --user --no-build-isolation .
py -m transferdata.web migrate
py -m transferdata.web collectstatic --noinput
```

Миграции добавят таблицы `control_*`, не удаляя `panel_*` и данные TransferData.
Если TransferData уже настроена, снова выполнять import_config не нужно.

## Перенос существующей ERP_to_DWH

Само обновление кода не переносит служебную БД со старого сервера/каталога.
После остановки старого worker сделайте экспорт из **старого каталога ERP_to_DWH**
с его рабочей конфигурацией и Python-окружением:

```powershell
py manage.py dumpdata control.databaseconnection control.etljob control.etlexecution control.etlexecutionlog control.etlauditlog --natural-foreign --output erp-export.json
```

Экспорт содержит настройки, SQL, задания и историю, но не пароли подключений,
не хэши паролей пользователей и не lease старого worker. Храните его с ограниченным
доступом. Пользователи, на которых ссылаются авторы/журналы, должны существовать
в ETL Dev с теми же логинами. Создайте недостающие учётные записи через `/auth/user/`;
не меняйте ID вручную. Для работы в портале нужны is_staff и соответствующие права.

Вернитесь в **каталог TransferData** и импортируйте экспорт:

```powershell
py -m transferdata.web import_erp_export C:\path\to\erp-export.json
```

Замените путь действительным. Импорт разрешён только в пустую ERP-подсистему,
откатывается целиком при ошибке и не меняет исходный файл. Он сохраняет PK
внутри control-таблиц и разрешает пользователей по логину, а не чужим ID.
Импортированные расписания выключены. RUNNING помечаются FAILED, PENDING —
CANCELLED, с объяснением необходимости проверки цели. Статусы завершённых
запусков и журналы сохраняются. Никакие перенесённые действия автоматически
не повторяются. Если старой служебной БД нет, настройте подключения/задания
через `/erp/`; импорт не требуется.

Секреты SQL Authentication ERP берутся по credential_reference из окружения
**ERP-worker**; проверка подключения из ERP-интерфейса выполняется web-процессом,
поэтому для неё те же переменные должны быть доступны и web. Значения из старой `.env` не загружаются автоматически и не
копируются в служебную БД. Настройте их защищённым способом под учётной записью
сервиса. Windows Authentication использует пользователя процесса. Шифрование SQL Server всегда включено. По умолчанию сертификат проверяется.
Если корпоративный сертификат не доверен, в каждом ERP-подключении можно явно
включить «Доверять сертификату SQL Server без проверки». Настройка применяется
и к проверке подключения из панели, и к загрузке через ERP-worker. Существующие
подключения сохраняют проверку сертификата до явного включения переключателя.
Настройки TransferData на ERP автоматически не распространяются.

## Запуск: один web, два независимых worker

Откройте три PowerShell в каталоге проекта под нужной сервисной учётной записью:

```powershell
.\windows\Start-Panel.ps1 -Mode web
```

```powershell
.\windows\Start-Panel.ps1 -Mode worker
```

```powershell
.\windows\Start-Panel.ps1 -Mode erp-worker
```

Web слушает `0.0.0.0:8003`. Открывайте `http://vm-dwh:8003/` или разрешённый IP.
ERP-worker сам проверяет ежедневное расписание каждые 30 секунд и использует
исходные schedule_key для защиты от повторной постановки за день. Старую задачу
`enqueue_scheduled_jobs` после переключения отключите. У worker раздельные OS-lock,
поэтому одна копия каждого может работать одновременно. Оба процесса используют
общий SQLite с тайм-аутом; долгие SQL-транзакции выполняются во внешних СУБД.

Сначала проверьте подключения отдельно в каждой подсистеме и выполните
контролируемую загрузку в тестовое назначение. Потом включайте расписания.
Настройку трёх постоянных процессов можно выполнить через Task Scheduler
аналогично `windows/PANEL.md`, с перезапуском при сбое, без ограничения времени
и под той же Windows-учётной записью для DPAPI/Windows Authentication.

## Проверки

```powershell
py -m transferdata.web check
py -m transferdata.web test transferdata.web.panel
```

Для разработчика: `uv sync --locked`, `uv run pytest -q`. Реальный SQL Server
интеграционный тест ERP включается отдельно через `ETL_RUN_MSSQL_TESTS=1` и
MSSQL_TEST_* на изолированной тестовой базе; он создаёт и удаляет тестовую таблицу.
Без доступа к тестовому SQL Server он явно пропускается. Объединение проверено
локальными тестами; существующие Windows БД и реальные ERP→DWH загрузки из
облачной среды не проверялись.

Исходный код ERP импортирован с зафиксированного коммита; ссылка и адаптации
зафиксированы в `docs/ERP_UPSTREAM.md`. Исходный репозиторий ERP_to_DWH не изменён.
