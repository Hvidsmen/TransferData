## Архитектура публикации

Имена и типы рабочих объектов остаются прежними — **таблицы**, а не views/synonyms:

- `1CUnloading.1c.[РегистрСведений.ЦеныНоменклатуры]`;
- `DataWH.erp.[РегистрСведений.ЦеныНоменклатуры]`;
- `DataWH.erp.PriceERP`.

В шаге будет одна команда:

```sql
EXEC [DataWH].[price_trial].[RefreshAndPublish];
```

Сначала Refresh обновляет проверенное состояние trial. ApplyStage в той же
транзакции добавляет изменённые ключи и старые/новые группы в постоянную очередь
PendingKeys/PendingGroups. Очередь накапливает изменения между всеми Refresh,
а не хранит только последний запуск. Затем PublishPending применяет её ко всем
трём рабочим таблицам одной локальной межбазовой транзакцией. Технический столбец
`__etl_terminal` не публикуется. Последние интервалы обновляют конечную дату и
при нулевых изменениях.

Если Refresh успешен, а публикация упала, прежние рабочие данные сохраняются,
очередь остаётся. Следующий RefreshAndPublish сможет повторить публикацию.
PublishPending можно вызвать отдельно для повторения уже подготовленной дельты,
не читая ERP заново. Не очищать очередь вручную. Ручной старый Refresh после
переключения только подготовит дельту; он **не заменяет** RefreshAndPublish.

Все процедуры используют один session applock в DataWH. Он защищает наш путь,
но не останавливает внешние скрипты и прежнюю процедуру ERP. После переключения
нельзя параллельно запускать старый шаг или менять рабочие таблицы другим писателем.
Читатели с NOLOCK/READ UNCOMMITTED могут видеть незавершённые изменения; транзакция
не исправляет режим изоляции чужого отчёта. Прямые чтения trial не означают, что
production уже опубликован: для этого есть LastPublishedAsOf и Publications.

## Подготовка: без переключения и без чтения регистра

На **vm-dwh**:

```powershell
cd "C:\Users\ETLadmin\Desktop\TransferData"
git pull --ff-only origin main
```

В SSMS последовательно открыть с диска и выполнить целиком:

1. `tools/sql/Install-PriceTrial.sql` — обновляет ApplyStage, сохраняя существующие
   140 млн строк trial. Не запускать старый Test-PriceTrial на загруженном trial.
2. `tools/sql/Install-PricePublication.sql` — создаёт выключенную публикацию,
   очередь, процедуры и таблицу резервных команд. Не меняет рабочие строки/Agent.
3. `tools/sql/Test-PricePublication.sql` — маленький тест настоящего DML-движка
   через `Fixture=1`. Все назначения — временные таблицы текущей сессии. Проверяются
   изменение, удаление, переименование, NULL-группа, соседние интервалы, авария после
   записи первой копии, откат/повтор и запуск без изменений. Ожидается `PASS`.
4. `tools/sql/Check-PricePublication.sql` — структура, свойства, владелец шага,
   другие статические упоминания цен и свободное место **также для 1CUnloading**.
   Ранее проверяли прежде всего DataWH/tempdb; этого недостаточно для новых индексов
   и публикации в журналируемую таблицу 1CUnloading.

Check отказывается работать с несовпадающими типами/порядком столбцов, активными
триггерами, FK, RLS, temporal, CDC, Change Tracking или репликацией. Это повод
разобрать конкретную особенность, а не отключать её ради скрипта. Другие найденные
упоминания нужно проверить: поиск не доказывает отсутствия динамических/внешних
писателей. Установщик не расширяет права и не включает межбазовое ownership chaining.
Учётная запись шага должна иметь EXECUTE новых процедур и SELECT/INSERT/DELETE/UPDATE
рабочих таблиц во всех нужных базах. Dynamic SQL проверяет права вызывающего.

## Само переключение

В отдельное окно обслуживания, когда job закончил работу и нет других писателей,
выполнить **`tools/sql/Switch-PriceJob.sql`**. Это уже меняющий конфигурацию скрипт.
Его не следует запускать одновременно с Refresh, публикацией или повторным Switch.

Он выполняет следующие действия:

1. Проверяет машину, GUID/имя job, номер/тип шага, ожидаемую прежнюю команду и
   отсутствие активного запуска в последней сессии Agent.
2. Сохраняет полную строку sysjobsteps и прежний enabled в
   `price_trial.JobStepBackup`. Каждая попытка имеет отдельный CutoverId. Последние
   параметры восстановления дополнительно находятся в PublicationControl.
3. Временно отключает только этот job, чтобы расписание не запустило старую команду
   во время проверки. Повторно проверяет гонку со стартом. Ручные старты во время
   обслуживания запрещены; disabled сам по себе не блокирует sp_start_job.
4. В транзакции блокирует локальные рабочие таблицы на запись и полностью сверяет
   все три с trial, включая multiplicity дубликатов и байтовые значения названий.
   Реальный PriceERP проверяется напрямую: только подвижная конечная дата последней
   записи приводится к AsOf trial. Старые конечные даты допускаются в диапазоне
   AsOf+9…11 лет; все остальные значения/интервалы должны совпасть. Также проверяется
   отсутствие одинаковых периодов внутри legacy-групп товар+вид цены.
5. Создаёт по одному уникальному некластерному индексу ключа на **каждой из трёх
   рабочих таблиц**, если их ещё нет. Это реальная индексация 140 млн строк, требует
   места и журнала и может занять часы. Индексы не добавляются на ERP. При конфликте
   определения одноимённого индекса скрипт отказывается продолжать.
6. Проверяет, что команду шага никто не изменил, включает журналирование дельты,
   меняет только команду шага 1 и восстанавливает прежний enabled.

Коммит шага, флага публикации и enabled выполняется одной транзакцией на одном
SQL Server. Нет CREATE VIEW, DROP TABLE, переименования или полной перезаписи цен.
Нет запуска первого обновления внутри Switch. Итог — строка **SWITCHED**, GUID,
BackupId, JobEnabled и новая команда. Если ранее job был выключен, останется выключен.

Повторная полная сверка нужна несмотря на предыдущий MATCH: trial и production
с того времени могли обновиться. Это не ещё одна загрузка из ERP. Проверка и
индексация могут занять несколько часов. Табличные shared locks запрещают изменение
проверяемых данных до коммита. Долгие чтения могут помешать фазам индексации;
таймаут получения блокировок 15 секунд, а не автоматическое убийство чужих запросов.
При обычной ошибке транзакция откатывается, команда остаётся прежней, enabled
восстанавливается. Откат большой индексации тоже может занять время.

Скрипты выполнялись только через T-SQL-парсер при подготовке; реальный SQL Server
в облачной рабочей среде недоступен. Перед Switch обязателен маленький fixture на
vm-dwh. Первое обновление после Switch контролировать вручную по обычному запуску
job (не создавать одновременно второй RefreshAndPublish). Публикация добавит
время к прежним 57–96 минутам; это отдельный замер, особенно при ненулевой дельте.

## Проверка состояния

```sql
USE [DataWH];
SELECT Active,LastPublishedAsOf,SwitchedAt,RolledBackAt
FROM price_trial.PublicationControl;
SELECT TOP (5) * FROM price_trial.Publications ORDER BY CompletedAt DESC;
SELECT s.step_id,s.step_name,s.command
FROM msdb.dbo.sysjobsteps AS s
WHERE s.job_id='DBDF6C37-D349-4123-B4AC-29302CD125AD' AND s.step_id=1;
```

Успех Refresh в Runs не является успехом публикации. Для этого нужны запись
Publications и успешный итог Agent. Publications содержит только успешные публикации;
при сбое смотреть ошибку Agent и наличие очереди. Session applock не переживает
обрыв соединения, а данные/очередь фиксируются транзакциями.

## Откат и восстановление после обрыва

Выполнить **`tools/sql/Rollback-PriceJob.sql`**, когда job не работает. Скрипт
проверит, что текущая команда — новая или сохранённая старая; посторонние изменения
не перезаписываются. Восстановит прежнюю команду и enabled, выключит публикацию.
Никакой job не запускается и не останавливается. Trial, очередь, индексы и резервные
команды не удаляются. Следующий обычный запуск прежнего шага вновь выполнит полную
старую загрузку и может удалить новые индексы при DROP/SELECT INTO — это ожидаемо.

Это **откат команды**, а не восстановление исторической версии 140 млн строк:
последние успешно опубликованные данные остаются в том же формате. Каждая публикация
атомарна; неуспешная не должна оставлять одну копию обновлённой, другую старой.
Для возврата данных на дату нужна штатная резервная копия БД, этот пакет её не заменяет.

При аварийном закрытии SSMS/сервера после временного отключения job обычный CATCH
может не выполниться: job останется disabled. После окончания отката SQL Server
выполнить Rollback-PriceJob, который использует заранее сохранённую команду. Нельзя
просто включать job, не проверив команду и Active. Если резервная запись отсутствует
или команду изменил другой администратор, автоматическое восстановление откажется.

После отката новая активация опять требует полной сверки. Сначала привести trial
и legacy к одному состоянию источника. Старую очередь можно очищать только после
успешной baseline-сверки внутри нового Switch; автоматически при Rollback она не
удаляется, поэтому следы неуспешной публикации остаются для разбора.
