# Обновление ETL Dev из браузера

Страница **«Обновление портала»** доступна суперпользователю в меню портала и по ссылке
на главной странице административной панели. Обычные пользователи запускать обновление
и читать его состояние не могут. Запуск требует POST с CSRF-токеном и подтверждения.

## Однократная установка на Windows

В PowerShell **от имени администратора под той же Windows-учётной записью**, что
используется задачами Web / TransferData / ERP / Python:

```powershell
cd "C:\Users\ETLadmin\Desktop\TransferData"
.\windows\Update-Portal.ps1
.\windows\Install-PortalUpdater.ps1
```

Первый вызов получает версию с этой функцией; установщик создаёт отдельную задачу
**ETL Dev — Update**. Он один раз запросит пароль текущей Windows-учётной записи,
чтобы задача могла работать с повышенными правами и сетью без открытого сеанса.
Пароль хранится планировщиком Windows; в JSON, HTTP и исходники не записывается.
Сохранённые настройки Git/доступ к origin должны быть доступны этой учётной записи
в пакетном сеансе. Интерактивные запросы Git и pip при обновлении отключены.

Установщик не заменяет существующую задачу с тем же именем и не запускает обновление.
Отдельная задача нужна потому, что обновление останавливает и запускает сам веб-процесс;
обычный дочерний процесс Web мог бы быть остановлен вместе с ним.
Нормальному токену той же учётной записи предоставляется чтение/запуск этой задачи,
но не её редактирование. При другой учётной записи веб-процесса требуется отдельная
настройка прав администратором Windows.

## Работа в браузере

Откройте страницу обновления, подтвердите ожидание активных операций и перезапуск,
нажмите **«Обновить портал»**. Запускается только фиксированная задача планировщика:
команды, пути, ветки и аргументы от браузера не принимаются.

Страница показывает этап, число завершённых этапов и журнал со временем. Это прогресс
**по этапам**, а не оценка оставшегося времени. Повторные клики блокируются файловой
блокировкой и настройкой `IgnoreNew` планировщика. При неопределённом тайм-ауте запуска
блокировка сохраняется: это не разрешение запускать второе обновление.

Обновление выполняет существующий Update-Portal.ps1: проверка задач и main, fetch,
пауза новых операций, ожидание подтверждения паузы обработчиками, остановка, резервная
копия, fast-forward обновление без reset, зависимости, миграции, static, check,
помощник 1С и восстановление прежних состояний служб. Задания, которые до обновления
не работали, автоматически не запускаются.

Во время ожидания завершения операций Web остаётся доступным. POST/другие изменения
на время обслуживания блокируются, просмотр и чтение статуса остаются доступными.
Во время установки и перезапуска Web недоступен: страница сохраняет последний
полученный этап и переподключается сама. Отсутствие связи не объявляется успехом
или доказательством неудачи.

## Состояние и сбои

Запросы и безопасный журнал этапов сохраняются в `.state/portal-update/runs` независимо
от процесса Web; отметки времени UTC показываются в браузере по Москве. Подробные
PowerShell transcript `.log` остаются только на сервере. Этот каталог ограничен
учётной записью ETL Dev, администраторами и SYSTEM, через HTTP журналы не выдаются.
Для резервного копирования состояния активный каталог portal-update исключается:
он содержит открытые эксклюзивные блокировки. Файл установки portal-updater.json
в корне .state сохраняется в резервной копии.

Если сбой произошёл до изменения кода/зависимостей, скрипт пытается восстановить
предыдущее состояние задач. После начала изменений сохраняется прежнее поведение
Update-Portal.ps1: задачи остановлены и отключены, maintenance.flag остаётся, чтобы
не запускать загрузки на частично обновлённом приложении.

В таком случае Web тоже может не запуститься, и браузер не сможет получить финальную
ошибку до восстановления сервера. Нужна диагностика на Windows по журналу, резервной
копии и состоянию задач; автоматического отката нет. Нельзя удалять блокировки,
maintenance.flag или запускать второе обновление, пока не проверена первая задача.
После восстановления та же страница покажет сохранённое состояние.

Проверки механизма без реального обновления: `pytest tests/test_portal_update.py` и
`pwsh -File tests/windows/Test-Updater.ps1` (модель планировщика, без остановки служб).
Реальные Windows-права/пакетный вход проверяются при однократной установке на сервере.
