# Пробная загрузка товаров коммерческих предложений по версиям документов

Скрипт `tools/sql/Trial-CommercialOfferLinesDelta.sql` — эксперимент на vm-dwh.
Он не меняет Agent, источники, рабочие erp-таблицы, представления и price_trial.
Создаёт приватный кеш и сравнивает результат с полной исходной загрузкой.

## Основание для эксперимента

Проверенный локальный join дал MATCH, но только 29 секунд выигрыша: baseline
8,237 мин, candidate 7,750 мин; исходный запуск первым мог прогреть кеш кандидата.
Рабочий шаг документов не переключён. Следующее направление — уменьшить именно
объём ежедневного переноса 7 млн строк, а не удалять быстрые индексы.

Предоставленные метаданные ERP:

- шапка `_Document80440`: уникальный `_Document80440_S_HPK` по
  `_Fld2951, _IDRRef`; `_Version` — NOT NULL `timestamp`, 8 байт;
- товары `_Document80440_VT80488`: уникальный `_Document80440_VT80488_SK` по
  `_Fld2951, _Document80440_IDRRef, _KeyField`;
- `_LineNo80489` — номер строки, **не подтверждённый уникальный ключ**.

`timestamp` здесь означает rowversion, а не дату. Код сохраняет его как обычный
`binary(8)`, чтобы локальная копия не стала автоматически обновляемым timestamp.
Сравниваются версии по равенству, без правила «больше максимальной версии».
Поэтому уменьшение значений версии после восстановления базы не игнорируется.
Однако повторное использование версии в другой ветке восстановленной БД и
прямые записи только в табличную часть этим не исключаются: полная сверка остаётся.

## Что делает кандидат

1. Читает узкий полный список ключей и версий шапок, без 27 соединений и DocumentKey.
2. Сравнивает его с предыдущим **проверенным** состоянием. Находит новые документы,
   документы с другой версией и физически исчезнувшие ключи, включая разделитель.
3. Только для этих владельцев читает товары, пакетами до 100 ссылок одного
   разделителя через OPENQUERY. В запросе на ERP стоят оба условия:
   `_Fld2951 = ... AND _Document80440_IDRRef IN (...)`. Это позволяет использовать
   префикс исходного ключа и не требует передачи всех строк для локального фильтра.
   RPC OUT не включается, хранимые процедуры на ERP не создаются.
4. Заменяет весь набор товаров изменённого документа: удаляет старые строки кеша
   этого владельца и вставляет текущие. Обрабатываются добавление/исправление,
   удаление строк и пустая табличная часть. Нельзя использовать максимальный номер
   строки как идентификатор. Сырой `_KeyField` сохраняется в кеше и его ключе;
   тип наследуется от источника, а не угадывается.
5. Перечитывает три маленьких справочника и заново расшифровывает локальный кеш.
   Это учитывает переименования справочников при неизменной версии документа.
   Сохраняются все три LEFT JOIN, NULL, дубликаты и прежние преобразования дат.
6. Материализует отдельный результат из 56 прежних столбцов и строит два индекса.
   Служебный `_KeyField` в пользовательский результат не добавляется.

Источник с сырыми строками без соответствующей шапки не поддерживается такой
моделью версий. Обнаруженные полученные строки без родителя вызывают отказ.
Новые сиротские строки вне запрошенных владельцев, пропущенные изменения
табличной части и прочие расхождения должны обнаруживаться полной сверкой.
Логическая пометка удаления не трактуется как физическое удаление: если шапка
существует, действующие строки сохраняются по исходной семантике view.

## Запуск

```powershell
cd "C:\Users\ETLadmin\Desktop\TransferData"
git pull --ff-only origin main
```

В SSMS на **vm-dwh**, в новом окне без транзакции, выполнить целиком
`tools/sql/Trial-CommercialOfferLinesDelta.sql`. Требуется schema/marker от ранее
выполненного Measure-CommercialOffers. Должно быть стабильное состояние ERP и
справочников, без восстановления исходной базы/параллельных загрузок.

**Первый запуск — `initial_full`**: он создаёт весь кеш. В режиме full все шапки
показываются как AddedDocs, это инициализация, а не число новых бизнес-документов.
На первом запуске оценивать правильность, а не выигрыш инкрементальной загрузки.
**Следующий запуск — `incremental`**. После естественных изменений источника
прислать Mode, AddedDocs, ChangedDocs, DeletedDocs, FetchedRows, CandidateMinutes,
ValidationResult и две величины различий. MATCH при нуле изменённых документов
не доказывает поведение при редактировании/удалении товаров.

Каждый запуск отдельно делает **полную эталонную копию** исходного представления
и полную сверку. Поэтому весь опыт по-прежнему читает все товары. Это цена
проверки, а не скрытая часть инкрементального кандидата: CandidateMinutes включает
узкое чтение шапок, чтение дельты, справочники, запись кеша, расшифровку и индексы,
но не включает полный эталон и сверку. BaselineMinutes — полный путь с индексами.
IncludingValidationMinutes — длительность опыта целиком. Эталон идёт первым,
поэтому кеш/нагрузка также могут влиять на сопоставление времени.

Места потребуется больше, чем в предыдущем тесте: постоянный сырой кеш около
размера строк товаров плюс индекс и компактный кеш шапок, **ещё две полные копии
результата на каждый запуск** (ранее около 8 GiB вместе), а также tempdb и журналы.
Все временные staging-таблицы находятся в одном динамическом batch и освобождаются
после него. Готовые пробные результаты/журналы автоматически не удаляются.

## Сверка и доверие к кешу

Каждый раз сверяются все 56 видимых столбцов с независимым исходным view: типы,
порядок, длины, precision/scale/collation, значения и multiplicity дубликатов.
Текст/бинарные данные проверяются побайтно с длиной, без хешей и sampling.
Служебный `_KeyField` не является столбцом исходного view и не участвует в этой
сверке пользовательского результата. Сверка может занять десятки минут отдельно
от времени кандидата, как в предыдущем опыте с 34-минутной проверкой.

Обновление сырого кеша, снимка версий и checkpoint выполняется одной локальной
транзакцией; удалённые чтения закончены до неё. После коммита checkpoint имеет
**Verified=0**, затем строится результат и выполняется полная проверка. Только
MATCH/0/0 переводит checkpoint в Verified=1. Если после записи кеша запрос оборван,
сверка упала или нашла различия, состояние остаётся непроверенным. Следующий
обычный инкрементальный запуск откажется его использовать.

После разбора ошибки можно явно изменить `@ForceFull` с 0 на 1 и выполнить
скрипт заново для полного восстановления приватного кеша (`forced_full`). Это
не подтверждение корректности сигнала версии: такой запуск опять читает всю
табличную часть. Если ошибка произошла до коммита обновления кеша, прежнее
проверенное состояние сохраняется и полный сброс может не требоваться.
При изменении схемы сырого источника нужен отдельный разбор типов кеша; ForceFull
перечитывает данные, но не выполняет автоматическую миграцию типов.

1С должна обновлять версию шапки при сохранении изменений табличной части.
**Один лишь SQL timestamp этого не обеспечивает**: прямой UPDATE дочерней таблицы
не обновляет родителя автоматически. Зелёный MATCH на нескольких наблюдавшихся
состояниях полезен, но не является доказательством для всех будущих способов
записи. До подтверждения этого контракта и подготовки публикации в production
рабочий шаг оставляем прежним; эту полную проверку не отключать ради скорости.

Нет общего snapshot разных удалённых чтений. Если источник изменился между
эталоном и кандидатом, различия могут быть следствием разной свежести. Выбирать
готовую статичную ERP-копию; не применять NOLOCK и не обходить проверку.

## Прогресс

```sql
USE [DataWH];
DECLARE @run uniqueidentifier = (
    SELECT TOP (1) RunId FROM document_trial.OfferDeltaRuns ORDER BY StartedAtUTC DESC
);
SELECT * FROM document_trial.OfferDeltaRuns WHERE RunId=@run;
SELECT Phase,Status,RowsCopied,
    CAST(DATEDIFF_BIG(millisecond,StartedAtUTC,
        COALESCE(CompletedAtUTC,SYSUTCDATETIME()))/60000.0 AS decimal(14,3)) AS Minutes
FROM document_trial.OfferDeltaPhases WHERE RunId=@run ORDER BY StartedAtUTC,StepNo;
SELECT * FROM document_trial.OfferDeltaState;
```

Время журнала UTC. Статус running сам по себе не доказывает активность запроса.
При отмене session applock может остаться до закрытия исходной сессии; не запускать
параллельные повторные опыты и не удалять кеш/журналы для «оживления» запроса.
Не удалять отдельные таблицы кеша: неполный комплект будет отклонён. Скрипт не
запускает, не останавливает и не отключает рабочие задания.

Скрипт проверяется T-SQL-парсером при подготовке. Реальный SQL Server и семантика
версий проверяются на vm-dwh; в облачной рабочей среде такого SQL Server нет.
