# Пробная загрузка цен на vm-dwh

Подготовлен отдельный SQL-вариант для проверки идеи: ежедневно читать исходный
регистр целиком, но расшифровывать только изменившиеся записи и пересчитывать
интервалы только затронутых групп. Ускорение пока не измерено. При большом числе
изменений сравнение и обслуживание таблиц могут оказаться медленнее полной загрузки.

Скрипты работают в `DataWH.price_trial`. Они не изменяют задания Agent, расписания,
ERP, `1CUnloading`, действующие `DataWH.erp` или кубы. Установщик создаёт только
схему, служебные таблицы и две процедуры; установка не запускает чтение источника.
SQL Server должен поддерживать `CREATE OR ALTER PROCEDURE` (2016 SP1+).

## Подтверждённые исходные данные

- ERP: linked server `erp-db-02.erp.lcl`, база `ERPBAckUp2`, регистр `_InfoRg48935`.
- 140 313 419 строк в каждой из трёх действующих таблиц цен.
- Уникальный ключ: `_Fld2951, _RecorderTRef, _RecorderRRef, _LineNo`.
- Поля версии/времени изменения в предоставленной структуре нет. Наличие CDC,
  Change Tracking или другого журнала этим не исключено, но не подтверждено.
- Индексы с именами `missing_index_*` уже существуют. Скрипт их не меняет.
- Окно будущего утреннего ETL: 07:00–10:30 по Москве. Первичная проба и полная
  сверка выполняются вне этого окна. Кубы оставлены на последнюю очередь.

## Порядок проверки

1. Обновить checkout на сервере:

   ```powershell
   cd "C:\Users\ETLadmin\Desktop\TransferData"
   git pull --ff-only origin main
   ```

2. В SSMS на **vm-dwh** открыть и выполнить
   `tools/sql/Install-PriceTrial.sql`. Обновление веб-портала для этого не нужно.
3. До первой реальной загрузки открыть и выполнить `tools/sql/Test-PriceTrial.sql`.
   Тест использует только маленькие локальные искусственные таблицы. Он проверяет
   начальную загрузку, исправление старой записи, удаление, добавление, переименование,
   перенос записи в другую группу, подвижную конечную дату и сохранение состояния
   при ошибке. В конце тест удаляет только созданные им таблицы данных trial.
   Если реальные trial-таблицы уже существуют, тест отказывается работать.
4. До чтения 140 млн строк DBA должен проверить свободное место в DataWH, журнале
   и tempdb. Trial хранит исходное состояние, расшифрованные цены и интервалы;
   временные копии, индексы, EXCEPT/UNION и сортировки требуют дополнительного места.
   Нет основания считать, что существующего свободного места достаточно.
5. Выбрать стабильное состояние источника: без восстановления ERPBAckUp2,
   обновления справочников и параллельного изменения исходных цен. Обычный linked
   server SELECT не обеспечивает согласованный снимок разных баз/справочников.
   Не использовать NOLOCK. Trial не создаёт журналы изменений и не меняет ERP.
6. В отдельном окне SSMS вне утренней нагрузки выполнить:

   ```sql
   USE [DataWH];
   EXEC price_trial.Refresh @AllowFullSourceRead = 1;
   ```

   Это **реальное полное чтение** источника и запись пробных данных. На первом
   запуске все записи новые, поэтому перерасчёт полный. Выполнение не ограничено
   коротким таймаутом и может занимать часы. Остановка запроса может вызвать
   длительный откат; не запускать рядом с утренним ETL ради быстрого теста.
7. Результат возвращает SourceRows, RawChangedKeys, EnrichedChangedKeys,
   RebuiltGroups, RunId и длительность фаз. Повторить trial на неизменном источнике,
   затем после штатных изменений. Именно повторные запуски проверяют полезность
   подхода. Прогресс не означает готовность: ориентироваться на успешное завершение.
8. При стабильных одинаковых источниках и готовой действующей загрузке выполнить
   `tools/sql/Compare-PriceTrial.sql`. Полная сверка также тяжёлая: группировка всех
   строк и независимый расчёт старой формулы интервалов используют tempdb.
   Нельзя сравнивать trial и production, снятые с разных версий источника.

## Семантика и ограничения

Сравнение исходных записей точное через EXCEPT в обе стороны, без хешей. Исчезнувшая
запись считается удалённой **только после успешного полного чтения** staging. Пустой
источник по умолчанию отклоняется. Частичный, но успешно прочитанный источник
(например, копия базы ещё не готова) автоматически распознать нельзя: готовность
источника должна быть подтверждена до запуска. Все изменения постоянного состояния
trial фиксируются одной транзакцией. Ошибка оставляет предыдущее состояние.

В расшифровке сохранены три LEFT JOIN по ссылке, преобразование года 1С, все строки,
включая неактивные, характеристики, валюты и разделитель. Если справочник содержит
повторяющиеся ссылки, trial останавливается: он не выбирает произвольное имя и не
меняет соединение на ссылку+разделитель без проверки действующей семантики.
Изменения, добавления и удаления названий справочников тоже инвалидируют записи.
Названия сравниваются по байтам, включая регистр и завершающие пробелы.

`price_trial.Prices` соответствует 15 столбцам `erp.[РегистрСведений.ЦеныНоменклатуры]`.
`price_trial.Intervals` содержит эти столбцы, DateStart, DateEND и технический бит
`__etl_terminal`. Последний столбец не является частью пользовательской схемы.

Группировка интервалов сохранена буквально: **название товара + название вида цены**,
порядок только по периоду. Характеристика, валюта и разделитель в неё не добавлены.
При одинаковом периоде порядок в исходном LEAD неоднозначен; trial также не
изобретает приоритет записей. Сверка возвращает число таких групп и требует
отдельного решения перед переключением, даже если значения совпали.

Конечная дата последней записи — время начала trial + 10 лет. Для неизменившихся
групп она обновляется отдельно через индекс TerminalRows. Поэтому интервалы не
«застревают» на дате первой загрузки. Сверка рассчитывает старую формулу на тот же
AsOf: сравнение с опубликованным PriceERP другого времени запуска дало бы ожидаемую
разницу конечных дат. Скрипт проверяет формулу по действующей таблице цен, а не
доказывает совпадение ранее опубликованной таблицы PriceERP с её источником.

Внутренний ApplyStage вызывается из Refresh. Он не предназначен для Agent и ручной
подачи произвольных данных. Все четыре temp-таблицы должны иметь структуру и порядок
столбцов из Refresh; синтетический тест показывает этот контракт. Session applock
исключает одновременные Refresh/ApplyStage и полную сверку одного trial. Он не
блокирует действующие загрузки и не заменяет согласованный снимок источника.

Runs хранит running/success/failed, число строк и номер SQL-ошибки; Phases — время
чтения регистра, справочников, сравнения/расшифровки, пересчёта интервалов и сохранения
состояния. Аварийный обрыв сессии может оставить Runs.status=running; это не команда
повторного выполнения и не доказательство активного запроса. Коммит данных и запись
итогового статуса не являются общей распределённой транзакцией.

## Что не сделано автоматически

- Не заменяется действующая процедура и шаг part 2.
- Не меняется расписание и не сокращается история цен.
- Не включаются CDC/Change Tracking, RPC OUT, SNAPSHOT, новые индексы ERP.
- Нет гарантии завершения к 10:30: требуется замер повторных запусков и сверка.
- Скрипты не выполнялись на реальном SQL Server при подготовке. SQL-тест нужно
  выполнить на vm-dwh перед загрузкой реальных данных.

Для отказа от эксперимента достаточно не вызывать Refresh: действующий путь не
переключён. Удаление больших trial-таблиц освобождает ресурсы с задержкой и должно
планироваться DBA вне нагрузки; скрипта автоматического удаления схемы нет.
