# Цепочки SQL-процедур

В разделе **Python обработчик** появился тип задания **Цепочка SQL-процедур**.
Существующие Python-файлы и обработчик коммерческих предложений не меняются.
Новый тип доступен и в полном ETL Dev, и в профиле etl-dev-yds.

## Создание и администрирование

Создайте задание, выберите тип «Цепочка SQL-процедур» и SQL-подключение из общего
справочника 1С. Все шаги используют одно подключение и его Windows/SQL-учётную
запись. У каждого шага можно указать свою базу на том же SQL Server, схему,
имя процедуры, таймаут и параметры. Обращения процедур к MSK-DB или связанным
серверам остаются внутри существующего SQL-кода. Портал подключается к выбранному
серверу, например MSK-DB2; доступность остальных серверов из этого не следует.

Шаги выполняются сверху вниз. Кнопки ↑/↓ меняют порядок; переключатель «Выполнять»
управляет постоянным пропуском. Для каждого шага задаются обязательные предыдущие
шаги. Зависимость от более позднего, отсутствующего или отключённого шага
блокирует сохранение/запуск. Идентификаторы шагов стабильны при перемещении.
Условия, не заданные в зависимостях, из SQL-кода автоматически не выводятся.

Параметры процедур задаются в JSON шагов: `"parameters": {"DateFrom":"2026-01-01"}`.
Это связанные параметры ODBC, а не фрагменты SQL. Пароли передавайте через
настроенные переменные окружения подключения, не через параметры шагов.
Процедуры указываются без EXEC и квадратных скобок. Внутренняя точка в имени
процедуры допустима: например `sp_РегистрБухгалтерии.Хозрасчетный`.

Редактирование активного задания блокируется. Каждый запуск сохраняет копию
конфигурации: изменения после завершения влияют на будущие запуски. На странице
запуска видны порядок, названия, полные имена процедур, статусы, время и результат
каждого шага. Вывод SQL-строк, значений параметров и результирующих наборов данных
в журнал не производится. Неуспешный SQLSTATE и ненулевой код RETURN показываются
без исходного текста ODBC-ошибки, который может содержать секреты. Ошибка
валидации профиля выводится с этапом «Подключение к SQL Server» и названиями
проверяемых полей без их значений. Если сбой произошёл до подключения, журнал
явно сообщает, что SQL-процедуры ещё не запускались.

## Пропуск и остановка

При ручном запуске появляется подтверждение со списком шагов. Можно пропустить
шаг только на этот запуск, не меняя задание. Зависимости проверяются повторно;
пропустить необходимую зависимость и запустить зависимый шаг нельзя.
Запуски по расписанию и массовые запуски используют сохранённый набор шагов.

У активного запуска есть «Остановить после текущего шага». Запрос не прерывает
текущую процедуру: она завершается, затем цепочка останавливается. Запуск в
очереди можно отменить до выполнения. Отдельной кнопки принудительного прерывания
SQL сейчас нет. Если превышен общий таймаут задания, дочерний процесс завершается,
а выполнявшиеся/не зафиксированные шаги помечаются как требующие проверки.
Откат на стороне SQL Server может продолжаться после завершения процесса.

## Транзакции и продолжение

**Одна транзакция на цепочку** — режим по умолчанию. Шаги до общего COMMIT имеют
статус «Выполнен, ожидает фиксации группы». При ошибке или остановке портал вызывает
rollback; продолжение с середины недоступно. Это сохраняет две точки фиксации
исходного скрипта, если он разделён на две предложенные цепочки.

**Фиксировать каждый шаг отдельно** — COMMIT после каждого успешного шага.
Предыдущие зафиксированные шаги сохраняются при ошибке следующего. Этот режим
изменяет семантику исходного скрипта и требует проверки процедур.

После завершения такого запуска доступно «Продолжить с выбранного шага».
Создаётся новый запуск со ссылкой на исходный; используются процедуры, порядок
и подключение из его снимка. Все включённые шаги перед точкой начала должны иметь
подтверждённую фиксацию; пропущенные шаги остаются пропущенными. Неоднозначный
или ошибочный шаг нельзя обойти выбором более поздней точки. Выбранный шаг и все
последующие включённые шаги выполняются заново: перед этим нужно подтвердить,
что результаты проверены и повтор допустим. Существующий активный запуск не
изменяется и не дублируется.

COMMIT в SQL Server и запись контрольной точки в служебной БД не являются одной
распределённой транзакцией. При потере связи во время фиксации или аварии между
ними результат помечается как неоднозначный. Автоматического повтора такого
шага нет. Перед ручным повтором проверьте данные в SQL Server.

Внутренние COMMIT/ROLLBACK процедур, внешние действия и обращения через связанные
серверы не могут быть отменены или проверены порталом автоматически. Даже успешный
вызов rollback на подключении не доказывает откат всех внутренних действий.
Проверка повторяемости процедуры остаётся обязательной перед запуском с середины.

## Два задания из предоставленного скрипта

В профиле **etl-dev-yds** обновление и первичная установка теперь создают
обсуждённые задания автоматически через `setup_sql_pipelines`. Оба задания
попадают в группу «SQL-процедуры», расписания выключены. Повторный запуск
сохраняет все правки, имена, архив и логическое удаление существующих заданий.
Системный идентификатор позволяет не создавать дубликат после переименования.

Для каждого задания используется активное подключение к MSK-DB2 и нужной базе,
если оно определено однозначно. Иначе создаются отдельные Windows-профили
`MSK-DB2 · 1С · процедуры` и `MSK-DB2 · DataWH · процедуры`, без паролей,
с установленным Driver 17/18 и включённой проверкой сертификата. Проверьте
их сервер, TLS и права EXECUTE перед ручным запуском. Существующие подключения
не изменяются. Новые служебные профили не становятся источниками каталога 1С.
Другие профили развёртывания автоматически эти задания не получают.

Вручную, без ожидания очередного обновления, после установки новой версии:

```powershell
cd "$env:USERPROFILE\Desktop\etl-dev-yds"
& .\.venv\Scripts\python.exe -m transferdata.web setup_sql_pipelines
```

Процедуры при подготовке не выполняются. Альтернативно в **Python → Задания** нажмите **«Создать цепочки из SQL-скрипта: Бухгалтерия и
DataWH»**, выберите подключение к MSK-DB2 и подтвердите создание.

Создаются два задания без расписаний и без выполнения процедур:

- **Бухгалтерия и ОС** — три процедуры в базе `1С`, исходный порядок;
- **Обновление DataWH** — семь процедур в базе `DataWH`, исходный порядок.

В примерах явно заданы зависимости обновления итогового отчёта по отпускам от
первого отчёта и план-факта БДР от факта. Для первых трёх процедур также сохранена
последовательная зависимость. Остальные взаимосвязи нужно проверить по SQL-коду.
Имена базы `1С`, схем и процедур следует сверить с реальным сервером.
Общий таймаут примеров — 6 часов, отдельного шага — 30 минут; измените по
реальным требованиям. Повторное создание не перезаписывает существующие задания.

Между двумя заданиями нет автоматической зависимости: не настраивайте их
расписания, предполагая гарантию «второе только после успеха первого».
Один Python-worker выполняет задания последовательно, но это не проверка
успеха другого задания. Первые запуски выполняйте вручную после проверки
результатов и межпроцедурных зависимостей.

После обновления портала выполняются миграции. Новые таблицы шагов и поля запусков
создаются без изменения истории существующих Python-заданий. Реальные процедуры
в облачных тестах не выполняются: транзакции, сбои COMMIT, остановки и продолжение
проверены с макетом SQL-подключения и реальной служебной БД Django.


## Диагностика SQL-ошибок и прогресс

Журнал показывает этап, имя шага, SQLSTATE и известные номера SQL Server
(например, 201 — обязательный параметр, 208 — объект не найден, 229 — права,
266 — несовпадение количества транзакций, 7391 — распределённая транзакция).
Текст драйвера, имена объектов из него и значения данных не сохраняются;
расшифровка берётся из фиксированного списка. Для старого запуска, в котором
сохранён лишь SQLSTATE, полный номер ошибки восстановить из журнала портала нельзя.

Ошибочный/неоднозначный шаг не увеличивает счётчик пройденных шагов. Например,
при сбое третьей процедуры после двух завершённых показывается 2 из 3, а не 100%.
Этот счётчик не доказывает COMMIT: итоговые статусы шагов и режим транзакции
видны отдельно. Количество записанных строк для процедур не вычисляется.
