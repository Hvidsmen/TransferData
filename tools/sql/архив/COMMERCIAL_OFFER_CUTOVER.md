## Что и как публикуется

Используется уже проверенный document_trial.OfferDeltaRawCache и HeaderCache.
Читается список версий всех шапок и товары только новых/изменённых/исчезнувших
владельцев, пакетами по 100 ссылок с разделителем на стороне ERP. Три небольших
справочника читаются полностью; расшифровка всего кеша учитывает переименования.
После удалённых чтений список версий шапок повторно сравнивается с первым:
при изменении источника загрузка отказывает до локальных записей. Это не общий
snapshot для справочников или защиты от прямого изменения дочерних строк.

Кеш, версии, checkpoint и **полная локальная замена** рабочей таблицы товаров
выполняются одной транзакцией. ERP читается до её начала; DTC не требуется.
Рабочая таблица не удаляется/переименовывается: её object_id, права и индексы
сохраняются. DELETE/INSERT выполняется с исключительной блокировкой таблицы;
обычные читатели могут ждать. NOLOCK не обеспечивает согласованное чтение.
На запись всех 7 млн строк нужны свободное место в журнале и время; обещать
ровно 2,95 минуты production-загрузки нельзя.

При ошибке до коммита откатываются товары, кеш и версии. Повторный запуск
снова видит ту же дельту. Скрипт не повторяет SQL автоматически. После отмены
в SSMS проверьте состояние транзакции/сессии: откат SQL Server может продолжаться.

Полная независимая сверка исходного view обязательна при переключении и затем
при первом запуске спустя семь дней после предыдущей успешной полной проверки.
Можно вызвать раньше: `EXEC DataWH.document_trial.RefreshOfferLines @FullCheck=1;`.
Она сравнивает все значения и количество дубликатов, а не хеши или выборку.
При расхождении публикация и изменение кеша откатываются; старые данные остаются,
шаг падает. Автоматического сокрытия ошибки полной перезагрузкой нет.
Полная проверка добавляет десятки минут к этому запуску и удерживает локальную
транзакцию кеша во время сравнения; учитывайте это в утреннем окне 07:00–10:30.

Одна успешная дельта не доказывает контракт всех способов записи: SQL rowversion
изменяется только в самой шапке. Изменение товаров без обновления шапки может
оставаться незамеченным до полной проверки. После восстановления ERP-копии,
изменения схемы или появления таких записей нужна внеплановая полная проверка.
Verified в OfferDeltaState означает именно полную сверку. После обычной
production-дельты он равен 0; доверенный production-checkpoint находится в
OfferPublicationControl.LastRunId и должен совпадать с PreparedRunId.
Пробный скрипт отказывается работать, пока Active=1, чтобы не сдвинуть этот кеш.

## Применение на сервере

Перед началом: исходная ERP-копия готова и стабильна, задания документов не
выполняются. У пользователя нужны прежние права чтения linked server и права
DDL/DML DataWH / изменения задания msdb. Контекст исполнения Agent остаётся
прежним; не включать TRUSTWORTHY или RPC OUT ради обхода ошибки прав.

```powershell
cd "C:\Users\ETLadmin\Desktop\TransferData"
git pull --ff-only origin main
```

Открывать файлы из `tools\sql` в SSMS на vm-dwh и выполнять **целиком**:

1. `Install-CommercialOfferPublication.sql` — создаёт процедуры и контрольные
   таблицы. Не читает ERP и не меняет рабочие данные или Agent.
2. `Test-CommercialOfferPublication.sql` — маленькие локальные тесты публикации:
   исправление, удаление, новые строки/дубликаты, пустой набор, сохранение
   object_id/индексов, реальная ошибка INSERT после DELETE с откатом checkpoint,
   отказ точного сравнения при лишнем дубликате. Ожидается **PASS**.
   В облаке SQL Server нет: этот тест надо исполнить на настоящем SQL Server.
3. `Switch-CommercialOfferJob.sql` — сохраняет полную строку шага msdb и исходный
   enabled, временно отключает задание от расписания, повторно проверяет отсутствие
   текущего запуска, выполняет дельту с полной независимой сверкой и публикует товары.
   Затем меняет только команду шага 41 и восстанавливает enabled. Ожидается **SWITCHED**.
   Задание не запускается и не останавливается скриптом. Это длительная операция,
   а не только мгновенная замена текста команды.

Команда шага должна совпадать с ранее предоставленной: две transferTalbeToDatWHErp
и пять индексов. Игнорируется только форматирование, скобки и разделители команд.
При отличии — остановка до изменений, пришлите текущую команду для разбора.
Старый шаг нельзя оставлять параллельным писателем в рабочую таблицу товаров.
При ошибке обновления команды после успешной публикации данные уже могут быть
обновлены, но исходная команда остаётся совместима с этими данными.

## Проверка и восстановление

```sql
USE DataWH;
SELECT * FROM document_trial.OfferPublicationControl;
SELECT j.name,j.enabled,s.step_id,s.command
FROM msdb.dbo.sysjobs j JOIN msdb.dbo.sysjobsteps s ON s.job_id=j.job_id
WHERE j.name=N'ERP to DWH Документы' AND s.step_id=41;
SELECT TOP(5) * FROM document_trial.OfferDeltaRuns ORDER BY StartedAtUTC DESC;
SELECT * FROM document_trial.OfferDeltaState;
```

После SWITCHED: Active=1, JobEnabled равен исходному, команда содержит
`EXEC [DataWH].[document_trial].[RefreshOfferLines]`. Журнал production включает
время полного контроля (если он был), локальной публикации и удалённых чтений;
сравнивать его CandidateMilliseconds с изолированным 2,95 мин напрямую нельзя.
Успешные промежуточные публикационные таблицы удаляются в той же транзакции.
При неудаче контрольная OfferAudit_<RunId> может остаться для разбора; не удаляются
автоматически ранее созданные результаты опытов. Статус running не доказывает
активность SQL: при обрыве сначала проверить сессию/транзакцию.

**Откат / восстановление после обрыва переключения:** в новом SSMS-окне выполнить
`Rollback-CommercialOfferJob.sql`. Он восстанавливает сохранённую команду и enabled,
Active=0, не запускает/останавливает job и не меняет данные. Если job работает —
дождаться завершения. Последняя успешно опубликованная версия товаров остаётся;
следующий старый шаг выполнит полное копирование. Сбой сессии/хоста между временным
отключением и завершением Switch может оставить задание отключённым — нужен этот
скрипт восстановления, а не запуск с неизвестным состоянием.

После отката исходный шаг DROP/SELECT INTO меняет object_id; новый Switch запишет
актуальный object_id. Для восстановления пропущенных изменений: после отката
запустить пробный скрипт с ForceFull=1 и дождаться MATCH, затем повторить Switch.
Частично удалять кеш/состояние нельзя. Backup-строки не перезаписываются.

## Быстрое переключение без повторной полной сверки

По запросу пользователя добавлен отдельный `Switch-CommercialOfferJob-Fast.sql`.
Сначала выполнить обновлённый `Install-CommercialOfferPublication.sql` (создаёт/
обновляет процедуры, данные и Agent не меняет), затем обновлённый
`Test-CommercialOfferPublication.sql` до PASS. Вместо обычного Switch выполнить
целиком **Switch-CommercialOfferJob-Fast.sql**. При предыдущей незавершённой попытке
сначала нужен штатный Rollback; уже полученный ROLLED_BACK достаточен, повторять
его перед обычной новой попыткой не требуется.

Fast требует реально записанного успешного полного MATCH в журнале и доверенного
checkpoint кеша. Сохраняет все проверки схемы/индексов, двойное чтение версий шапок,
исключение параллельных операций, резервную копию команды, локальную транзакцию и
восстановление исходного enabled. Не делает полную эталонную копию исходного view
и сравнение значений, поэтому не подтверждает совпадение с текущим полным источником.
Изменение только дочерних строк без смены версии шапки с момента старого MATCH
может быть пропущено. Это принятый компромисс быстрого переключения.

Дельта обновляется и все локальные итоговые товары по-прежнему записываются в
рабочую таблицу с индексами: время не сводится к мгновенной смене команды.
Успех: PUBLISHED / FullSourceChecked=0, затем SWITCHED / FullSourceChecked=0.
Новая отметка полной проверки не создаётся: Verified остаётся 0, LastFullCheckUTC
при отсутствии прежней даты берётся из LastVerifiedAtUTC последней полной сверки.
Еженедельная проверка в обычных запусках не отключается; если предыдущий MATCH
уже старше семи дней, ближайший рабочий запуск выполнит полную проверку.
Скрипт Rollback прежний. Обычный Switch остаётся с обязательной полной сверкой.


## Диагностика длительного переключения (обновление 20.11.2026)

После отменённого восьмичасового запуска журнал показывал успешное чтение ERP
и справочников примерно за 1,2 минуты. Участок повторного чтения/сравнения шапок
не имел отдельной фазы: именно после справочников и до apply_private_cache.
Причина восьмичасовой задержки после отмены не установлена; диагностический SELECT
в той же сессии уже не показывает прежний statement/wait. Утверждать, что причина
найдена и устранена, нельзя.

Добавлены отдельные фазы recheck_header_versions и compare_header_versions,
индекс второго снимка и сравнение индексированных ключей/версий вместо двух EXCEPT.
Добавлена фаза publish_live_rows и сообщения acquire_live_lock, delete_live_rows,
insert_live_rows. RunId/SessionId печатаются перед чтением ERP. В Messages сообщения
приходят сразу через NOWAIT, включая фазы внутри ещё незавершённой транзакции.

Локальное ожидание блокировки ограничено 30 секундами в переключении, публикации
и откате (SQL error 1222); установка процедур также ограничивает ожидание DDL.
Это **не общий таймаут выполнения**: вычисления, сеть, удалённое ожидание на ERP,
запись и откат могут занимать больше времени. Более короткий конечный timeout
вызывающего кода сохраняется; для Switch/Rollback используйте новое стандартное окно.
Ошибка откатывает локальную транзакцию; сам откат может быть длительным.

Вложенная публикация при переключении больше не захватывает ту же session-lock
повторно. Если окно уже удерживает эту блокировку, скрипт отказывает до нового
захвата и просит переподключение. SQL Cancel всё равно может обойти TRY/CATCH:
при отмене проверить транзакцию/откат и освободить исходное соединение, затем
выполнить штатный Rollback. Не делать KILL по старому номеру без проверки владельца.

После git pull выполнить обновлённые Install-CommercialOfferPublication.sql и
Test-CommercialOfferPublication.sql (до PASS), затем быстрый Switch в новом окне.
Он проверяет установленную версию диагностики. Через 2–3 минуты без нового сообщения
не ждать часами: в отдельном окне выполнить **Check-CommercialOfferOperation.sql**
и прислать CurrentStatement, wait_type, blocking_session_id и последние фазы.
При необходимости указать напечатанный SessionId в начале диагностического файла.
Журнал читается с READUNCOMMITTED, чтобы не ждать коммита операции: это только
прогресс, который может быть отменён, а не подтверждение успешной публикации.
Никакие процессы диагностический файл не завершает, настройки Agent не меняет.

## Ошибка 266 при выходе из динамического блока

В предыдущем варианте BEGIN TRANSACTION находился внутри sp_executesql, а COMMIT
в вызывающей процедуре. Возврат с изменённым @@TRANCOUNT приводил к сообщению 266.
Исправлено: кеш, материализация, проверка (когда включена), публикация, checkpoint,
очистка staging и COMMIT выполняются внутри одного динамического batch. В его
CATCH выполняется ROLLBACK; возврат к RefreshOfferLines происходит без открытой
транзакции. Защиты Switch требуют обновлённую версию OfferPublicationDiagnosticsV3.

Тест дополнен реальным sp_executesql с локальными fixtures: успешная публикация
возвращает @@TRANCOUNT=0, ошибка INSERT откатывает данные и checkpoint, также без
открытой транзакции. В облаке проверяются синтаксис и структурная регрессия границы
транзакции; сам SQL-тест нужно исполнить на vm-dwh.

При ошибке старого варианта в исходном SSMS-окне проверить @@TRANCOUNT/XACT_STATE;
если есть открытая транзакция именно этого переключения, выполнить ROLLBACK и
дождаться его завершения. Закрыть исходное соединение для освобождения session-lock,
затем выполнить Rollback-CommercialOfferJob.sql в новом окне. После ROLLED_BACK
обновить файлы, выполнить Install и Test до PASS, затем новый быстрый Switch.
