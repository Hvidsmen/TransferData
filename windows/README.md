# Развёртывание на Windows-сервере vm-dwh

Сценарий: Windows Task Scheduler запускает перенос SQL Server → PostgreSQL ежедневно
от имени `DAICHI\ETLadmin`. Windows-аутентификация использует учётную запись
процесса; отдельный пароль SQL Server не требуется. У этой записи должны быть
SELECT к исходной таблице и право входа в качестве пакетного задания.

1. Установите Python 3.12+ x64, uv и Microsoft ODBC Driver 18 for SQL Server x64.
   Разместите проект, например, в `C:\TransferData`. В PowerShell:

   ```powershell
   cd C:\TransferData
   uv sync --locked
   Copy-Item config.example.json config.json
   .\.venv\Scripts\transferdata.exe validate --config config.json
   ```

2. Проверьте `config.json`: источник `vm-dwh`, база `DataWH`, `auth: windows`;
   назначение PostgreSQL `83.166.255.19:5432`, база `analytics`. По умолчанию
   используется `public.contractors`. Команда `prepare` создаст таблицу по структуре
   источника; PostgreSQL-пользователю нужно право CREATE в схеме public.
   При отличающихся именах задайте `columns` в задании.
   SQL Server должен иметь доверенный сертификат на выбранное имя сервера.
   PostgreSQL требует доверенный сертификат, соответствующий IP либо DNS-имени:
   при необходимости замените IP на имя из сертификата и настройте `PGSSLROOTCERT`.
   Проверки сертификатов не отключаются.

3. Войдите на vm-dwh именно под `DAICHI\ETLadmin`. Сохраните пароль PostgreSQL
   локально через защищённый ввод (используйте новый пароль взамен опубликованного):

   ```powershell
   New-Item -ItemType Directory -Force .state | Out-Null
   Get-Credential -UserName 'd.ivanov' -Message 'PostgreSQL analytics' |
       Export-Clixml .state\postgres.credential.xml
   ```

   Windows DPAPI шифрует пароль для текущего пользователя и машины. Задача должна
   работать под той же учётной записью на той же машине. Ограничьте права NTFS
   каталога проекта и `.state` учётной записью задания и администраторами.
   Не публикуйте файл credential.xml. Скрипт передаёт пароль только в окружение
   дочернего процесса и затем восстанавливает предыдущие значения.

4. Проверьте подключение и выполните первый перенос в тестовую целевую таблицу:

   ```powershell
   .\windows\Run-Transfer.ps1 -Command check
   .\windows\Run-Transfer.ps1 -Command prepare
   .\windows\Run-Transfer.ps1 -Command run
   ```

   `prepare` создаёт только отсутствующую таблицу и не меняет существующую.
   Схема должна существовать. При неподдерживаемых типах команда завершится ошибкой;
   ключи, индексы, identity, триггеры и defaults не копируются.
   `run` выполняет полную замену данных. После загрузки проверьте число строк и
   значения, особенно даты, decimal, UUID, двоичные данные и длинные строки.

5. В Task Scheduler создайте задачу под `DAICHI\ETLadmin`: запускать независимо
   от входа пользователя, с сохранением пароля учётной записи (не режим S4U
   «не сохранять пароль», ограничивающий сетевые ресурсы/DPAPI). Права администратора
   самой задаче не нужны. Триггер — ежедневно в 02:00 по Москве; учтите часовой пояс
   Windows-сервера. Внешний планировщик использует свой триггер, поле cron JSON
   применяется только при команде `serve`. Включите запуск после пропуска времени.
   При уже работающем экземпляре — не запускать новый.

   Программа: `powershell.exe`

   Аргументы:
   ```text
   -NoProfile -NonInteractive -File "C:\TransferData\windows\Run-Transfer.ps1" -Command run
   ```

   Рабочая папка: `C:\TransferData`.
   Используйте принятую в организации политику выполнения/подписи PowerShell-скриптов.
   Код результата 0 означает успех, ненулевой — ошибку. Для постоянного журнала
   направьте stdout/stderr в систему сбора логов либо добавьте перенаправление
   в принятую у вас оболочку запуска с сохранением кода возврата.

Вместо Windows Task Scheduler можно запускать `-Command serve` под супервизором:
тогда используется cron из JSON. Одновременно оба варианта не включайте.

Тесты алгоритма выполнялись в Linux. Windows-аутентификацию, DPAPI, PowerShell
и реальный перенос необходимо проверить на vm-dwh; доступ к этому серверу из
облачной среды не предоставлен. Отказы подключения из облака не доказывают
недоступность PostgreSQL непосредственно с vm-dwh.
